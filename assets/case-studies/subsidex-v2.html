The problem

The Problem

Every handover needs a government-portal acknowledgement

India's fertilizer subsidy is paid by the government directly to manufacturers, but only once every handover in the plant → rake point → wholesaler → retailer → farmer chain is acknowledged on a government portal. DBT stretched that reconciliation cycle from under 30 days to 120+, and the entire process was still being run by hand.

01

Data moves faster than people can read it

The government portal updates constantly, but companies were only pulling it weekly or fortnightly.

02

Manual consolidation, manual errors

MIS teams hand-downloaded reports and rebuilt pending-acknowledgement lists in Excel — every step open to error.

03

Field officers act on stale data

By the time a nudge reached a wholesaler or retailer, the numbers behind it were already out of date.

"120+ days.
Still run by hand."

The problem wasn't new technology or missing data. It was that every piece of it was moving through human hands — slowly, inconsistently, with no visibility into what was falling through the cracks. The architecture needed to fix all of that at once.

Assumptions & Constraints I Designed Against

Assumptions

  • Data is available on the Govt. portals in the first place.
  • iFMS & MFMS refresh before 8 AM daily.
  • Notifications route via SMS, email, or the Khaad Dealer App.
  • Analytics access sits behind a separate re-login for that platform.

Constraints

  • Extraction is entirely dependent on portal uptime.
  • Data accuracy is capped by the accuracy of the source portal.
  • Any Govt. UI change means redevelopment of the scraping layer.
  • SMS & email delivery both depend on third-party providers.

Integration & Infrastructure Architecture

Hosted end-to-end on IBM Cloud infrastructure.

Integration & infrastructure architecture — IBM Cloud
The Path a Single Scraped File Takes
1

Subsidex is hosted and managed on IBM infrastructure as a cloud service.

2

The Scheduler stays connected to the RPA agent over JNLP; scraping jobs run on independent slave servers.

3

Files the RPA agent extracts are pushed to IBM file storage via the IBM SDK's REST API.

4

That upload fires an event that publishes a message onto IBM MQ via JMS.

5

The Data Processor is subscribed to that queue and pulls the matching file back down on arrival.

6

The processor validates, maps, and cleans the data, persisting it into Postgres via JDBC, per-tenant schema.

7

The same processor pushes the relevant data out over SMS and email via third-party APIs.

8

The portal client calls the web server for anything a user needs on screen.

9

The analytics dashboard reads straight from the relevant DB schemas through DB connectors.

10

Dashboards themselves are built on Microsoft Power BI.

The architecture wasn't just sound on paper. It had to hold against government portal downtime, third-party failures, and a data pipeline that couldn't afford to lose a single file. Security came next — not as an afterthought, but baked into every decision that came before.

Security & Compliance

Secure by design. Isolated by default.

Data Security

SSL encryption on all data in transit; encryption at rest with periodic key rotation.
Portal credentials encrypted at storage — entered directly by the client, never visible to any person.
AES-256 for critical data such as company iFMS credentials.
OAuth-based access to the Subsidex portal, tokens valid for 30 minutes to bound any leak.
A secure VPC around the entire platform, with client-managed role-based access via an admin portal.
Data security architecture

Multi-Tenancy

Each client gets a separate schema — logical, not physical, isolation.
Platform-level data lives in one shared schema that never carries client-specific data.
All tenants share the same underlying infrastructure, scaled horizontally or vertically as needed.
Multi-tenancy — schema-level isolation

Archival, Account Lifecycle & Access Control

Archival & Purging

  • Govt.-portal data persisted for a predefined period per data-set policy.
  • On contract termination, client data is retained 90 days, then purged.

Onboarding / Offboarding

  • Onboarding provisions a dedicated schema and admin accounts for the client.
  • Offboarding revokes all user access immediately; data persists 90 days before purge.

Role-Based Access

  • Client admins create roles with varied access levels.
  • Roles are assigned per employee to control what each person can reach.
"Every tenant's data:
isolated by design."

A platform carrying government credentials and financial reconciliation data had one non-negotiable: no tenant's data could ever touch another's. The security architecture answered that. Then it went further.
