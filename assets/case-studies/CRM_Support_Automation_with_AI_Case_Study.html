01 — The Problem

Resolution Was Manual, and It Was Slow

Ticket resolution depended entirely on people. That meant every ticket waited — including the large share of standard issues whose answers were already known.

MANUAL, ONE TICKET AT A TIME

Every ticket needed an agent, start to finish

  • An agent had to read the complaint, work out what had gone wrong, look up the transaction and write a reply — for every single ticket.
  • Standard issues with known answers sat in the same queue as genuinely new problems.
  • Resolution time and backlog both grew with ticket volume, across every app.
SUPPORT TEAM LOAD

Agents spent their day on repeats

The time that should have gone to complex, high-value cases went to answering the same questions again and again — and the only way to scale was more headcount.

MERCHANT TRUST

Waiting chipped away at confidence

For a merchant with a customer at the counter and money in question, every hour without an answer made the platform feel less dependable.

02 — Options Considered

What I Weighed Before Landing on a Tiered AI System

Each option fixed part of the problem. Only one fixed speed, scale and trust together.

Option A

Add more support agents

The simplest lever — more people, shorter queue.

Cost grows in step with volume, and agents still spend their time on repeat questions.

Option B

Rule-based auto-replies only

Canned responses triggered by keywords or error codes.

Fast and cheap, but brittle on free text, robotic in tone, and useless for anything new.

Option C

Let a large language model answer everything

One model reads every ticket and writes every reply.

High cost per ticket, slower, and hard to audit on money-related answers.

Chosen — Tiered AI Resolution

Rules where the answer is known, AI where it isn’t, people where it matters

Known error codes resolve automatically from approved answers; new issues go to an AI layer that researches the merchant’s real data; anything it can’t resolve goes to a human with the evidence already gathered.

Scales support without adding headcount — while keeping answers accurate, auditable and human in tone.

04 — Ways In

Three Ways to Raise a Complaint — and the Tech Behind Each

The same three entry points across every PayNearby app, so a merchant can raise an issue from wherever they already are.

04.1 · VOICE & CHAT

Speak It or Chat It — Why Bhashini

In the Raise Complaint section, a merchant holds the mic and speaks in their own language. Bhashini converts the speech to text and translates it, so every voice note reaches the system as a clean, readable ticket. Merchants who would rather type use the chatbot.

Why we chose Bhashini

  • Built for Indian languages — speech-to-text in 12 Indian languages and translation across 22: the languages merchants actually speak.
  • Government of India platform (MeitY) — a natural fit for a regulated fintech handling merchant and transaction data.
  • One API for the whole chain — speech recognition and translation from one provider, instead of stitching two vendors together.
  • Keeps the language tag — the source language is stored with the ticket, which later lets the reply come back in that language.

Why a chatbot too

  • Some merchants prefer typing, or are somewhere noisy. Guided questions (service, transaction ID) mean the ticket arrives structured.

04.2 · SCREENSHOT

Screenshot-to-Complaint — Context Without Typing

A screenshot is what a merchant takes anyway when they see an error. So the screenshot became the trigger: the moment one is taken, a Raise Complaint button pops up over the current screen, and one tap creates the ticket.

How it works

  • Android 14+ — the OS screenshot callback (Activity.ScreenCaptureCallback, with the DETECT_SCREEN_CAPTURE permission) tells the app the moment a screenshot is taken.
  • Older Android versions — the app watches for a new image landing in the device’s screenshots folder.

Why we attach app state, not just the image

  • Android’s callback doesn’t hand over the image — and reading an error off a picture is unreliable anyway.
  • So the app attaches what it already knows: the screen, error code and transaction ID. Classification starts with facts, not guesses.
  • Most screenshot tickets carry a known error code, so they go straight to automated resolution.

What the ticket carries

{
  "channel":     "screenshot",
  "app":         "<which PayNearby app>",
  "screen_id":   "<current screen>",
  "error_code":  "<shown on screen>",
  "txn_id":      "<if a txn was open>",
  "app_version": "…",
  "device":      "…",
  "screenshot":  <image file>
}

The screenshot is evidence; the app state is what gets it resolved

06 — Tech Deep-Dive · Classification

Mapping Every Ticket — Rules + Machine Learning

The engine has one job: decide, with confidence, whether this is a known problem. It does that two ways, depending on what the ticket carries.

Deterministic

Error-code mapping

  • When the ticket carries a system error code (screenshot payload, transaction record), it’s matched against a catalogue of known codes.
  • Each code has an approved resolution and the data it needs.
  • Why: exact, auditable and practically free — right for money-related issues.

Machine learning

Intent prediction

  • For free text (voice and chat), an ML model predicts the intent and gives a confidence score.
  • Trained on historical tickets that agents had already resolved.
  • Why: merchants describe the same problem a hundred ways — rules alone can’t keep up.
Confidence gate — a known code or high-confidence intent goes to L1 auto-resolve; anything below the threshold goes to the L2 AI layer. Why not send everything to a large language model? Cost per ticket, speed, and the need for repeatable, auditable answers when money is involved.

07 — Tech Deep-Dive · L1 Auto-Resolve

Answers That Read Like a Person Wrote Them

For known issues the facts are already settled — the work is in how the answer is said, and when.

01 · Template

Grounded template

Each known code has an approved resolution, filled with this merchant’s live data — amount, status, reference number.

Why: the facts are always correct and approved.
02 · Drafting

Human-like drafting

A generative AI step rephrases the template into a natural reply, without changing any of its facts.

Why: templates alone read like a bot.
03 · Language

Their language

The reply uses the language from the merchant’s previous tickets, translated through Bhashini.

Why: an answer in your own language feels personal.
04 · Timing

Smart delay

A delayed-job queue holds the finished reply and releases it 10–15 minutes after the ticket was raised.

Why: an instant reply looked like a bot — see below.

09 — Tech Deep-Dive · L2 AI Layer

When the Issue Is New — Retrieval-Augmented AI

For unknown issues the AI doesn’t guess. It first fetches this merchant’s real data, then answers only from what it found.

Where it looks

01

Transaction & ledger records

What actually happened to this merchant’s transaction.

02

Bank / partner status

Whether the bank or partner system confirmed, failed, or is still pending.

03

Knowledge base & SOPs

Current policies and fixes — usable the day they’re written, without retraining a model.

04

Similar past tickets

How agents resolved the closest matching cases before.

Guardrails

01
Answers only from retrieved data. If the evidence isn’t there, it doesn’t answer.
02
Personal details stay private. Personal and account details are masked before anything reaches the model.
03
Read-only by design. It can explain a transaction — it can never move or reverse money.
04
Knows when to hand over. Below the confidence threshold, a human takes over with a summary and the evidence already gathered.
Why retrieval, not a bigger model: answers are grounded in this merchant’s own data, and a new SOP works the day it’s written.
